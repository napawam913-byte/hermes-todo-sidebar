# 通用聊天与周期计划 Skill/Tool 设计

## 决策摘要

桌宠中的 AI 入口改为通用 Hermes 对话，不再默认把每轮消息限定为周期任务创建模式。只有用户明确表达“创建、制定、安排、生成或调整计划”的操作意图时，Hermes 才加载周期计划 Skill，并调用周期计划提案 Tool。

周期计划 Tool 只产生标准变更提案，不直接写入本地数据。桌面端继续负责严格校验、提案预览、用户确认和原子写入。仅仅讨论健身、学习、饮食或某个目标时，Agent 正常交流，不生成提案，最多主动询问一次是否需要制定计划。

## 目标

- 让 Hermes 成为主要聊天 Agent，而不是周期任务专用表单助手。
- 让周期计划能力按自然语言意图自动出现，不要求用户手动切换模式。
- 复用现有 `AiMutationProposal v1`、操作白名单和 `AppMutationExecutor`。
- 保持“模型不能绕过确认直接写入”的安全边界。
- 为未来服务器数据库、飞书同步和更多领域 Skill 保留统一扩展方式。

## 非目标

- 本阶段不允许 Hermes 自动提交或永久删除本地数据。
- 本阶段不把完整本地数据库长期复制到 Hermes 会话或记忆。
- 本阶段不实现飞书、系统提醒、具体时间或跨设备同步。
- 本阶段不把通用聊天扩展成任意桌面控制工具。

## 三种实现方向

### 方案 A：通用聊天 + Skill + 提案 Tool（采用）

Hermes 正常聊天，明确计划意图出现时加载 Skill，并调用提案 Tool。Tool 返回标准提案，桌面端确认后写入。

优点：符合 Agent 工作方式；聊天自然；可复用现有提案与事务执行层；未来可继续增加学习、饮食等 Skill。缺点：需要新增 Hermes Skill、Tool 适配器和桌面端协议识别。

### 方案 B：保留通用聊天与计划模式开关

用户手动选择“普通对话”或“周期计划”，计划模式继续使用当前强制提示词。

优点：实现简单、行为确定。缺点：用户必须理解模式，聊天过程中无法自然进入计划能力，不符合本次方向。

### 方案 C：Hermes 直接写服务器数据库

周期计划 Tool 直接修改云端数据库，桌面端只同步结果。

优点：适合最终多端同步。缺点：当前数据仍在 Windows 本地；需要服务端数据库、权限、审计、同步和冲突处理，不适合作为第一步。

## 用户交互规则

### 不触发 Tool

以下表达只进入普通聊天：

- “最近想开始健身。”
- “新手一周练几次比较合适？”
- “我在学习某个教程的第三章。”
- “你觉得我的饮食有什么问题？”

Agent 可以分析、建议和追问，但不生成周期计划 JSON。

### 建议但不触发 Tool

当讨论已经形成稳定目标，但用户没有明确要求创建计划时，Agent 最多询问一次：

> 需要我把这些建议整理成可加入桌宠的周期计划吗？

用户没有确认时继续普通聊天，不重复推动创建。

### 触发 Skill 和 Tool

以下表达视为明确操作意图：

- “帮我制定一个四周的入门健身计划。”
- “把这些内容安排成未来七天的学习计划。”
- “创建一个每周三次的训练周期任务。”
- “把现有健身计划改成每周四练。”

信息充分时直接调用提案 Tool；信息不足时每轮只追问一个关键问题，补齐后再调用。

### 确认规则

- Tool 调用成功后进入提案页，不直接修改数据。
- 用户点击“确认执行”后，桌面主进程才进行原子写入。
- 用户放弃提案后清除待执行缓存，不修改任何计划。
- 永久删除继续显示不可恢复警告，并要求显式确认。

## Hermes Skill 设计

Skill 建议安装在：

```text
~/.hermes/skills/cycle-plan/SKILL.md
```

Hermes 会从 `~/.hermes/skills/` 发现 Skill，并在描述与当前请求匹配时按需加载。Skill 不是固定话术模板，而是包含触发条件、步骤、工具选择、禁止事项和验证规则的程序性说明。

建议的 Skill 元信息：

```yaml
---
name: cycle-plan
description: Create or adjust confirmed date-based cycle-plan proposals.
version: 1.0.0
platforms: [linux]
metadata:
  hermes:
    tags: [todo, planning, productivity]
    category: productivity
---
```

Skill 必须包含以下规则：

1. 只有明确的创建或调整意图才能调用 Tool。
2. 仅讨论计划主题时正常回答，不调用 Tool。
3. 信息不足时每次只追问一个关键问题。
4. 第一版只生成 `YYYY-MM-DD` 日期，不生成具体时间和提醒。
5. 不生成数据库 ID、时间戳、来源、`proposalId` 或确认状态。
6. 不声称已经创建成功；必须等待桌面端确认结果。
7. Tool 失败时说明失败原因，不伪造提案。

## Tool 设计

优先使用 Hermes 自定义 Plugin 或同机 MCP 服务提供 Tool，不修改 Hermes 核心源码。

模型负责把自然语言计划整理成 Tool 参数；Tool 负责严格校验、限制作用域并包装成标准提案。Tool 不再次调用模型，也不访问 Windows 本地文件。

### `cycle_plan.propose_create`

用途：生成新的周期计划提案。

输入为模型根据用户对话生成的标准草稿：

```json
{
  "draft": {
    "title": "四周入门健身计划",
    "topic": "健身",
    "description": "每周三次，循序渐进",
    "status": "active",
    "entries": []
  }
}
```

输出为不含 `proposalId` 的 `ModelMutationProposal`：

```json
{
  "schemaVersion": 1,
  "summary": "创建四周、每周三次的入门健身计划",
  "operations": [
    {
      "type": "cyclePlan.create",
      "draft": {
        "title": "四周入门健身计划",
        "topic": "健身",
        "description": "每周三次，循序渐进",
        "status": "active",
        "entries": []
      }
    }
  ]
}
```

### `cycle_plan.propose_adjust`

用途：只针对一个已存在周期计划生成调整提案。

输入必须包含 `targetPlanId`、目标计划的 `updatedAt` 和受限的计划操作数组。目标计划快照由桌面端在用户明确进入“AI 调整”时作为临时上下文提供。输出只能操作该计划及其条目，不能修改其他计划或普通待办。

### 不向模型开放提交 Tool

第一阶段不提供 `cycle_plan.commit`。确认执行由桌面应用调用现有 `AppMutationExecutor`，避免模型把“建议”“可以”或其他含糊表达误判为写入授权。

## Hermes 响应传输合同

当前 OpenAI 兼容接口的非流式响应只稳定提供最终 assistant 文本，因此第一阶段不依赖前端读取 Hermes 内部 Tool 事件。

- 普通聊天：assistant 返回普通文本，桌面端作为 `message` 显示。
- Tool 成功：Skill 要求 assistant 把 Tool 返回的 `ModelMutationProposal` 原样作为唯一最终内容，不附加代码围栏、前言或后记。
- 桌面端先尝试识别严格提案 JSON；完全符合合同时进入 `proposal`，否则按普通文本显示。
- 内容包含 `schemaVersion` 或 `operations` 等提案特征但校验失败时，必须显示格式错误，不能降级成普通聊天，以免用户误以为已经创建。
- 不依赖 Hermes 转发 `response_format`；本地严格解析器始终是最终安全边界。

未来若切换到 Hermes Runs API 或独立 Proposal Inbox，可以改用结构化事件传输，但不改变 `ModelMutationProposal`、预览确认和原子执行合同。

## 数据流

```text
用户消息
  -> 桌面端通用聊天会话
  -> Hermes API
  -> Grok 4.5 正常回答或 Hermes 加载 cycle-plan Skill
  -> cycle_plan.propose_create / propose_adjust
  -> ModelMutationProposal
  -> 桌面主进程严格校验并补充 proposalId、ID、时间戳和来源
  -> renderer 展示提案
  -> 用户确认
  -> AppMutationExecutor 克隆、校验、原子保存
  -> 今日待办按日期读取新周期条目
```

## 桌面端状态与界面

- AI 对话入口默认显示“助手”或“对话”，不显示“生成新的周期任务”作为全局标题。
- 顶部 `今日待办 / 周期任务` 导航继续保留；通用 AI 会话状态位于两者之上，不因切换页面或收起桌宠而销毁。
- 普通回复只显示聊天消息。
- Tool 产生提案后，`提案 N` 标签出现并可进入预览。
- 从周期计划详情点击“AI 调整”属于显式调整意图，可直接携带目标计划上下文进入对话。
- “已连接”改为实时连接状态；仅保存过配置时显示“配置已保存”。
- SSH 隧道或 Hermes 断开时显示离线状态，不把旧连接测试结果当作在线状态。

## 上下文与隐私

- 普通聊天默认不发送全部待办和周期计划。
- 创建新计划只发送当前日期、用户指令和必要约束。
- 调整计划只发送目标计划，不发送其他无关计划。
- API Key、桌宠位置、UI 状态和本地文件路径不进入模型上下文。
- 对话和未确认提案仍只保留在当前应用会话，重启后清除。

## 协议兼容

- 内部唯一正式合同继续是 `AiMutationProposal v1`。
- Hermes Tool 返回 `ModelMutationProposal`；桌面主进程负责补充 `proposalId`。
- 允许在供应商适配边界把 `version: 1` 或 `version: "1.0"` 规范化为 `schemaVersion: 1`，规范化后仍执行完整严格校验。
- 其他未知外层字段、未知操作、越权目标和超过 50 项操作继续整批拒绝。

## 异常处理

- Skill 未加载：保持普通聊天，不生成提案。
- Tool 不可用：显示“计划工具当前不可用”，保留聊天内容和输入草稿。
- 返回格式错误：主进程拒绝，不能进入确认页。
- SSH/Hermes 断开：显示离线状态，允许重试，不清除已有提案。
- 目标版本冲突：整批回滚，并提供读取最新计划后重新生成入口。
- 重复 Tool 调用：使用会话 ID 与 Tool 调用 ID 去重，不生成两个相同待确认提案。

## 分阶段实施

### 第一阶段：通用聊天与提案路由

- 移除桌面端全局周期任务强制提示词。
- 增加通用聊天请求与普通文本响应。
- 保留从计划详情进入的显式调整上下文。
- 增加 Tool 提案适配器，继续复用本地确认和原子执行。

### 第二阶段：Hermes Skill 与 Tool

- 在云端安装 `cycle-plan` Skill。
- 通过 Hermes Plugin 或同机 MCP 注册两个提案 Tool。
- 验证自然语言触发、追问和工具调用轨迹。

### 第三阶段：服务端数据与同步

- 把数据网关替换为服务器 API 和数据库。
- 桌面端通过同步层读取状态，Hermes Tool 访问同一服务端合同。
- 再接入飞书记录、长期任务和跨设备同步。

## 测试与验收

### 意图矩阵

- “我想开始健身”只正常聊天。
- “一周练几次合适”只提供建议。
- “需要我整理成计划吗”最多主动询问一次。
- “帮我制定四周计划”触发创建 Tool。
- “把这个计划改成四练”只触发目标计划调整 Tool。

### 安全与数据

- Tool 调用后、确认前，本地状态保持不变。
- 非法 JSON、未知字段、越权操作和超过 50 项均拒绝。
- 确认后只写入一次；任一操作失败整批回滚。
- 普通聊天请求不包含全部本地数据或 API Key。

### 交互

- 普通回复与提案状态区分清楚。
- 收起桌宠、切换页面后保留会话和未确认提案。
- 离线、生成中、Tool 不可用和冲突状态都有明确反馈。
- 长对话中输入区始终可见，消息区独立滚动。

## 最终边界

Hermes 可以决定调用什么能力，但不能决定是否正式写入。Skill 决定何时使用计划能力，Tool 生成可验证提案，桌面端和用户共同决定是否提交。这一边界在未来接入服务器、飞书或更多领域 Skill 后仍保持不变。
